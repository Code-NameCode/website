The problem

Batch pipelines are fine until a customer is on the phone.

Nobody chooses a five-minute refresh. It arrives quietly: a pricing page that is stale for a ticketing window, a support agent reading a fulfilment state that changed four minutes ago, a fraud rule that fires after the money has moved. Northbeam removes the batch from the path of the decision.

The product

Three surfaces. One state.

Write a rule once and Northbeam applies it to ingestion, to the client subscription, and to the alert. You are not maintaining the same logic in three languages.

01 / Ingest

Connect a source, not a pipeline

Kafka, Postgres change data capture, webhooks, Redis and S3 all land in the same namespaced topic. Backpressure is handled by the platform, so a 10× traffic spike does not become your 3 a.m. problem.

  • Exactly-once replay for every source, with a 30-day window
  • Schema guard rejects unknown fields instead of writing nulls into your schema
  • One CLI to inspect what arrived and what was rejected

02 / State

Declare the shape, not the plumbing

Define a channel, its state and the events that may change it. Northbeam maintains it, versions it, and replays it to any client that reconnects mid-flight. No WebSocket code in your application, no missed-update bugs.

  • Reconnect without gaps — clients resume from the last sequence they saw
  • Typed over the wire, generated for TypeScript, Go and Python
  • Bounded memory per channel, with eviction you configure rather than discover
channel · order.status
channel order.status {
  state: { status, updated_at, seq }
  on order.paid   → { status: "paid" }
  on order.shipped → { status: "shipped" }
  on order.cancelled → { status: "refunded" }
  retain: 30d · replay: on
}

03 / React

Push it to the browser, and to the pager

One subscription feeds the customer-facing widget, the internal dashboard and the alert route. When a channel breaches a threshold you set, the same event pages the on-call engineer — with the state attached.

  • Three lines of client code: useChannel("order.status", …)
  • Alert fatigue controls — grouping, hysteresis and quiet hours per route
  • Full replay of any customer's timeline for support and disputes

How it works

Live in an afternoon, boring after that.

This is the whole path. There is no cluster to size, no message broker to run, and no schema migration to schedule.

  1. Connect a source

    Paste a Postgres connection string or a Kafka bootstrap list. Northbeam maps the tables it can read and shows you the rest.

    nb connect postgres://…

  2. Declare a channel

    Point at the events that change your state. The playground replays a week of history so you can see the effect before it ships.

    nb channel order.status

  3. Subscribe

    Install one package, pass a channel name, render the state. Reconnects, ordering and gaps are the platform's problem again.

    useChannel("order.status")
